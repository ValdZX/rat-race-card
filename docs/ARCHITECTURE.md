# Поточна архітектура

## Платформи й технології

Rat Race Card — Kotlin Multiplatform застосунок із Compose Multiplatform для Android, iOS, Desktop JVM і Web/Wasm. Онлайн-сервер працює на Ktor/Netty JVM. Зв’язок клієнта із сервером реалізований через kotlinx-rpc поверх WebSocket, моделі серіалізуються kotlinx.serialization.

## Модулі

| Модуль | Відповідальність |
|---|---|
| `composeApp` | Точки входу платформ, DI-композиція, вибір режиму, очікування налаштувань і локалі. |
| `core` | Тема, компоненти, ресурси, платфорні `expect/actual`, RPC-клієнти, KStore й базовий Redux. |
| `card` | Локальний режим фінансової картки, `RatRace2CardStore`, локальні моделі та екрани. |
| `board` | Онлайн-клієнт: `BoardViewModel`, дошка, картки, діалоги, сторінки активів і візуалізація. |
| `shared` | Спільні серіалізовані моделі, формули й RPC-контракти. |
| `server` | Авторитетні правила онлайн-гри, черга, зберігання, генерація й WebSocket API. |

`card` і `board` не залежать один від одного. Обидва використовують `core`; `server` залежить від `shared`, але не від клієнтського модуля `board`.

## Онлайн-потік даних

```text
Compose UI
  → BoardViewModel
  → RaceRatService RPC
  → RaceRatServiceImpl
  → Storage
  → Event / GlobalEvent
  → BoardViewModel
  → StateFlow<BoardState>
  → Compose UI
```

`Board` містить стан партії й короткоживучий сценарій ходу: активного гравця, кубик, доступні колоди, взяту картку, аукціон, ставки та учасників ринкової події. `Player` містить фінанси, активи, професію, сім’ю, позицію, конфігурацію й прогрес.

Сервер оновлює гравця під mutex конкретного гравця, а дошку — під mutex конкретної дошки. Після зміни гравця виконується перевірка перемоги. `GlobalEvent` синхронізує всіх учасників, а `Event` передає персональні повідомлення, підтвердження й UI-ефекти.

## Авторитетність правил

Основний центр правил — `RaceRatServiceImpl`. Він:

- перевіряє чергу й допустимість команд;
- кидає кубик і рухає фішку;
- виконує ефекти клітинок;
- змінює гроші й активи;
- керує колодами, скидом, ринковими подіями та аукціоном;
- переходить до наступного гравця;
- перевіряє перемогу.

Частина передумов дублюється на клієнті для доступності кнопок, наприклад `canBuy`, `needPayExpenses` і `canMakeBid`. Сервер перевіряє чергу та багато параметрів команд, але деякі обмеження добровільної купівлі й `businessLimit` зараз покладаються на клієнтський UI. Це відома прогалина: недовірений клієнт не повинен мати можливості обійти такі правила, тому перевірки потрібно перенести в чистий рушій на ранній фазі рефакторингу.

## Контент карток

Механічні DTO карток оголошені як `sealed class BoardCard` у `shared`. Дефолтні картки живуть у Kotlin-мапах модуля `board`, а сервер знає старі колоди лише опосередковано через їхні ID та параметри, передані під час створення дошки. Для згенерованої партії сервер записує повні механічні картки в `Board.generatedCards`.

Локалізований текст відділений від механіки. `GeneratedText` зберігає назви й описи за локалями; клієнт накладає їх на механічну картку. Якщо згенерованої картки немає, `board` використовує дефолтну мапу колоди.

## Дошка та геометрія

`PlaceType` — sealed-ієрархія 17 типів клітинок. `BoardLayer` — enum із `INNER` і `OUTER`, який одночасно зберігає level, кількість і дефолтний список клітинок. Згенерована дошка може змінити порядок через `generatedPlaces`, але не склад і не кількість.

Клієнтська геометрія окремо знає розміри двох прямокутних треків. Іконки, кольори, підписи, звуки та візуальні розміри вибираються через `when (PlaceType)`.

## Генерація

Генерація має два шари:

1. LLM створює й проходить валідацію `GeneratedBalance`.
2. Детермінований `BoardGenerator` із seed будує механічні картки, професії, мрії та порядок клітинок.

Тексти генеруються окремо й можуть доганяти механіку через збережені чекпоінти. Клієнт слухає легкий прогрес і отримує повну дошку після значущих змін.

## Зберігання й сумісність

Онлайн-стан зберігається через серверний `Storage` у MongoDB або Firestore/Cloud Storage. Серіалізовані класи мають дефолти для нових полів. Деякі старі дані підтримуються евристиками, наприклад розпізнавання корупційної землі без явного прапорця.

Локальний режим використовує JSON у KStore. Він має власні `Business`, `Land`, `Shares`, `Fund` і `Config`, тому зміни спільної економіки не переходять у нього автоматично.

## Поточні точки зв’язності

Додавання одного механічного типу зараз торкається багатьох місць:

| Розширення | Типові зміни |
|---|---|
| Нова клітинка | `PlaceType`, кодек, серверний `when`, дефолтні списки, генератор, геометрія, іконка, колір, текст, звук, debug UI, тести. |
| Новий вид картки | `BoardCard`, генератор, текстовий brief, серверний RPC-метод, клієнтський front, `BoardViewModel`, події, дефолтна колода, тести. |
| Нова колода | `BoardCardType`, створення дошки, мапа `decks`, серверний вибір, UI стопок, генерація, локалізація й тести. |
| Нове коло | `BoardLayer`, `PlayerLocation`, розкладка, генерація, умови переходу, камера, геометрія, debug UI і тести. |

Великий `RaceRatServiceImpl`, широкі sealed-типи та exhaustive `when` дають хорошу статичну перевірку, але створюють високу ціну розширення. Наступний документ описує міграцію до реєстрів функцій, декларативного контенту й чистого ігрового рушія.
